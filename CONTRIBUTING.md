# Contributing to Free for Creators

Thanks for helping keep this list useful! There are two golden rules:

1. **Edit `data/*.json`, never `README.md` / `README.zh-CN.md`** — both READMEs are generated by `scripts/build_readme.py` and CI rejects drift.
2. **Verify the license yourself** before submitting. "Free" must mean free for the stated use (see the criteria below).

## Adding a resource

You can either open an issue with the [Suggest a resource](../../issues/new/choose) template (no git needed), or send a PR:

1. Pick the right category file in [`data/`](data). New category? See [Adding a category](#adding-a-category).
2. Append an entry object (fields below). Keep entries in a sensible order. Set `license_checked` (today's date) and `license_source` (the page you read the licence at) — the pair is what lets the next person re-check the claim instead of re-deriving it, and CI requires both on a new entry.
3. Regenerate every derived file:

   ```bash
   python3 scripts/build_readme.py   # README.md, README.zh-CN.md, banner counts
   python3 scripts/build_site.py     # site/all.html, site/sitemap.xml, site/data/
   ```

4. Commit the JSON and the regenerated files, then open a PR. CI validates the data against `schema/entry.schema.json`, checks that the READMEs / `site/all.html` / banner counts are all in sync, and a bot link-checks the URLs your PR adds and comments the results on the PR (❌ broken links block the merge; ⚠️ *blocked* means the site refused our bot or needs a human in a browser — verify those once).

### What CI checks on your PR

Two bots judge a submission, and they judge different things:

| Check | Workflow | Enforces |
| --- | --- | --- |
| Submission contract | [`pr-contract.yml`](.github/workflows/pr-contract.yml) | **One** entry per PR; a title of the form `[Resource name] -> [Category]` that matches that entry; a body carrying `Link: <the entry's URL>`, an answer to `Is this your product? Yes / No`, and — for an addition or a change to a licence claim — the **verbatim licence wording** and the **page it was read at**, which must match the entry's `license_source`; every checklist box ticked; and a file list limited to `data/**`, the two generated READMEs and `assets/social-preview.html` |
| New-link check | [`pr-linkcheck.yml`](.github/workflows/pr-linkcheck.yml) | Every URL the PR adds resolves. ❌ broken blocks the merge; ⚠️ *blocked* is a bot wall (403/429/timeout) and needs one human look in a browser |

Then [`ci.yml`](.github/workflows/ci.yml) re-validates the data against the schema, re-audits entry quality, checks the READMEs are in sync, rebuilds the site payload and re-renders every page in headless Chrome at each breakpoint.

**Maintainers and bot accounts are exempt from the contract check**, because a category addition, a `CONTRIBUTING.md` edit and the weekly link-check commit are all legitimate PRs that are not resource submissions. If the file you need to change is outside that list, say so in the PR and a maintainer can merge it.

The checker's own rules are tested (`python3 -m unittest discover -s tests -t .`), including one test that fails if [`.github/PULL_REQUEST_TEMPLATE.md`](.github/PULL_REQUEST_TEMPLATE.md) stops carrying a confirmation the checker requires — so the gate is literal-minded only as long as it reads the template you were actually given.

### Processing a suggestion (maintainer checklist)

When something arrives through the issue template, run the *whole* loop — shipping the entry but leaving the issue open is the classic failure mode:

1. **Verify against the source, not the submission text.** Fetch the homepage and the license page named in the issue. For open-source projects the repo's own `LICENSE` is authoritative: `gh api repos/OWNER/REPO/license --jq .license.spdx_id`.
2. **Add the entry** with the `license`, `license_family`, `attribution`, `monetization` and `signup` values verification actually supports, and put the limits (no resale, no AI training, credit required, account needed after N downloads) in `notes` / `notes_zh`.
3. **Run the gate:** `python3 scripts/check_entry.py --all --offline`. It enforces the parts of the criteria a schema cannot: no unverifiable quantity claims ("thousands of") or empty superlatives, `conditional` monetization must have its condition recorded somewhere, `contains_cc0` implies `license_family: mixed`, `noncommercial` implies `not-allowed`, URLs canonical and untracked and unique, and every entry has a `description_zh`. CI runs the same command, so a violation cannot reach `main` — but catching it here saves a red build. To check a candidate *before* it is written into `data/`, use `--candidates` with a JSON file of `{file, entry, evidence}` objects; that mode additionally requires `evidence.quote` (the licence wording you read), `evidence.source` (where you read it) and, whenever `signup` is not `"unknown"`, `evidence.signup_how`.
4. **Regenerate** both derived sets: `python3 scripts/build_readme.py && python3 scripts/build_site.py`.
5. **Commit with `Closes #N`** in the message and push. Without that keyword GitHub will not close the issue for you.
6. **Comment on the issue** with what you verified, where the entry now lives, and the limits you recorded — then close it by hand if step 5 did not catch it.
7. **Cannot verify the license? Say so and leave the issue open.** Guessing a license is worse than a missing entry; note what was ambiguous so it can be revisited.

## Inclusion criteria

A resource belongs here when all of these hold:

- **Legally free** for at least some real creator use (commercial or clearly-marked non-commercial) — no pirated packs, no "free download" mirrors of paid products, no cracked assets.
- **The license is discoverable** on the site. If you cannot find terms, it does not go in the list.
- **Directly useful to creators**: assets, media, templates — not tools/services that merely touch media (those belong in sister lists like `free-for-dev`).
- **Stable URL**: link to the canonical landing page, no affiliate links, no tracking parameters, no URL shorteners.
- **Not a duplicate** of an existing entry (URLs are checked globally by CI).

Borderline AI-generated asset sites: include only when the site states an explicit license for its outputs.

Two categories are deliberately wider than "an asset file you download": **Search Engines** lists meta-search over openly licensed media, and **Colors & Gradients** lists palettes and gradients as copyable values (a palette you paste into a design is an asset; the licence on the palette data is what the columns record). The test stays the same — does a creator use the thing *in* a project? A colour picker, a mockup generator or a file converter is not that, and stays out.

### What does not count as free

This list exists because "free" on an asset site is ambiguous, so the lower bound has to be written down. The linked functionality is **not** free in the sense this list means when any of these is true:

- it is a **time-limited trial** — free for N days, then it stops working;
- it runs on **credits that expire**;
- it is capped by a **recurring quota** — N downloads a day, N exports a month, N minutes of render;
- it is capped by **storage** — a free workspace that cannot hold a real project;
- the output is **watermarked**, or exportable only at a resolution or format that is not usable;
- the **essential step is paid** — you can create it for free but downloading, exporting or licensing it commercially costs money.

Two things deliberately do **not** disqualify a resource, and rejecting them would empty this list:

- **A pricing page, or paid features next to the free ones.** Describe only the functionality that works without payment. What is out is a product that is paid-only, or a free tier that locks the exact feature you are linking to.
- **Repeatable per-use limits.** A file-size ceiling, a page limit per run, one project at a time — allowed, as long as the resource can be used again and again without paying. Record the limit in `notes` / `notes_zh`.

State the limit, not just the verdict: `monetization: conditional` needs its condition written in `notes`, and a limit you could not establish stays unstated rather than guessed — a guess is the one error this repo must not make.

## Gaps already investigated

Some absences in the data are not oversights. These paths have been walked; do not re-walk them without new information — and if you do have new information (a different network, a licence page that has since appeared), the missing piece is almost always the same: **a first-party licence statement you can quote**. With that, an entry takes minutes.

## Entry schema

Single source of truth: `schema/entry.schema.json`. `scripts/build_readme.py` reads the required-field list, every enum and the description length limits out of that file, so editing the schema changes what CI enforces — there is no second copy to keep in sync.

| Field | Required | Values | Meaning |
| --- | --- | --- | --- |
| `name` | ✅ | string | Resource name |
| `url` | ✅ | `https://…` | Canonical landing page |
| `description` | ✅ | ≤160 chars, no `\|` | One-line "what is it" |
| `license` | ✅ | string | License name as the source states it, e.g. `CC0`, `Pixabay Content License`, `Various (per item)` |
| `license_family` | ✅ | `cc0` / `permissive` / `cc-by` / `site-free` / `mixed` / `noncommercial` | Controlled class of that license — drives the stats and the website's CC0 filter |
| `attribution` | ✅ | `required` / `not-required` / `varies` | Must you credit the author? |
| `monetization` | ✅ | `allowed` / `conditional` / `varies` / `not-allowed` | Safe in monetized content? |
| `signup` | optional¹ | `required` / `not-required` / `optional` / `unknown` | Account needed to download? |
| `notes` | optional | string | Caveats: free-tier caps, platform restrictions, … |
| `description_zh` | optional | ≤160 chars | Chinese description; `README.zh-CN.md` falls back to English without it |
| `notes_zh` | optional | string | Chinese caveats (fallback: `notes`) |
| `submitted_by` | optional | GitHub username | Credits whoever suggested the entry: it appears under [Contributors](#contributors) and beside the entry in both READMEs. Use it for community submissions — omit it when the maintainer adds an entry themselves |
| `contains_cc0` | optional | boolean | With `license_family: mixed` only: the site *does* host CC0/public-domain items, but they must be filtered per asset |
| `skip_linkcheck` | optional | boolean | Only for login-walled URLs; justify in the PR |
| `linkcheck_js` | optional | boolean | The page is a JavaScript app whose HTML contains no `<title>`/`<h1>`, so the checker cannot confirm content from a plain fetch. Status, redirects and soft-404s are still checked |
| `license_checked` | optional² | `YYYY-MM-DD` | The date this entry's licence wording was last read at its source. The weekly link check proves a URL resolves; only a human reading the page proves the licence still says what the entry claims. **Required on a new entry** |
| `license_source` | optional² | `https://…` | The page the wording was read at — the site's terms page, or a repository `LICENSE` file. Must be set whenever `license_checked` is, so every date traces back to what was read |

¹ Not enforced by the validator, but every current entry sets it — please fill it in. `unknown` renders as ❓ on the website, so use it only when you genuinely could not tell.

² The two travel together: `scripts/check_entry.py` rejects either one alone, and `--license-audit` splits the rest into *stale* (a date older than the budget — actionable, fails the run) and *unverified* (no date yet — a backlog that is reported, not failed, because entries predating the field have no honest date to carry):

```bash
python3 scripts/check_entry.py --license-audit --max-age-days 365
```

**The backlog is worked in risk order, and nothing is dropped for being unverifiable.** With
around 190 entries unchecked, the count alone says nothing about where to start, so the audit
sorts them by what a wrong claim would cost: `[risk 4]` is an entry promising monetized use, no
attribution and CC0 — a claim a reader has no reason to check for themselves — while one marked
*conditional, credit me* has already sent them to the source. `--all-unverified` prints the
whole list in that order, and the monthly [`license-audit.yml`](.github/workflows/license-audit.yml)
run puts the top of it in an issue.

Entries whose terms cannot be read **stay listed and stay counted**. A bot wall, a licence page
that only renders in a browser, or no published terms at all is a fact about the *source*, not a
reason to delete the entry — removing it would trade a visible gap for an invisible one, and this
project's argument is that the licence column is worth more than the entry count. What such an
entry does not get is a check date it has not earned. If somebody does eventually read the terms
and they say something else, the entry is corrected or removed like any other wrong claim.

Deliberately **one** credits list: the README's [Contributors](#contributors) section is derived from `submitted_by` alone. Corrections and dead-link fixes that add no entry are credited in the issue or PR that landed them, so there is never a second list to keep in sync with the first.

Semantics we use consistently:

- `monetization: conditional` — free commercial use **only under conditions** (credit link, free-tier caps, specific platforms like YouTube/Twitch). Put the condition in `notes`.
- `monetization: varies` — the site hosts mixed per-item licenses (marketplaces, CC aggregators), or you could not confirm that every license in the mix allows commercial use. When in doubt, use `varies`: over-claiming `allowed` is the one error this repo must not make.
- `attribution: varies` — some items need credit, some don't.
- `license_family` — classify the *license*, not the site's marketing: `cc0` = everything is CC0/public domain with no conditions; `permissive` = OSS licenses (MIT/Apache/OFL/ISC/UFL); `cc-by` = Creative Commons attribution/share-alike; `site-free` = the site's own free license (the `attribution` column says whether credit is needed); `mixed` = terms differ per item, or are not uniformly known; `noncommercial` = not free for commercial use (must pair with `monetization: not-allowed`).
- A `mixed` entry must not claim a blanket `monetization: allowed` unless every license in the mix permits commercial use (e.g. Google Fonts: OFL/Apache/UFL only). If some items are NC or unknown, use `varies`.

## Fixing problems

- **Dead link / license changed**: use the [Report a dead link](../../issues/new/choose) template or send a PR updating the entry.
- **Running the link checker locally**:

  ```bash
  python3 scripts/linkcheck.py             # everything
  python3 scripts/linkcheck.py --slug fonts  # one category
  ```

  CI runs it every Monday. Links returning 403/429, any 5xx, or a 202/204 (accepted, no document) are reported as *blocked* — bot walls and server-side states, manual check, and they do not fail the build. Only verdicts that cannot be explained by a bad day fail it: 404/410, DNS failure, a connection still refused on both methods, and a 200 whose own title says "not found". When the weekly check fails, a bot opens (or updates) an issue labeled [`link-check`](https://github.com/skyzhao1223/free-for-creators/labels/link-check) with the full broken-link report — fixing one of those is a great first contribution.

  **A local run is indicative; CI's run is the baseline.** `build_opener` inherits the environment's proxies, and on macOS that includes a system-wide proxy with no environment variable set — so `env | grep -i proxy` shows nothing while every request still leaves through it. The checker prints which proxy it is using, and `--no-proxy` turns it off. Neither mode reproduces CI, and they disagree in opposite directions; measured against all 200 entries on one machine:

  | Run | Result |
  | --- | --- |
  | through a local proxy | 146 ok / 52 blocked / 1 broken (3 network failures) |
  | direct, `--no-proxy` | 134 ok / 64 blocked / 1 broken (20 network failures) |
  | CI, US runner, no proxy | 127 ok / 53 blocked / **0 broken** |

  The proxy's exit IP is bot-walled by some sites — of ten `HTTP 403` verdicts sampled, eight were reachable straight from the host and two were plain 200 — while its routing reaches sites the host cannot: `itch.io` timed out on both paths and refused port 443 locally, yet CI has never reported it broken. Before concluding that a resource is dead, check it the other way and remember that CI is the run that gates the build.

  A status code alone is not enough, so the checker also looks at what came back:

  | Situation | Result | Why |
  | --- | --- | --- |
  | 200 whose own `<title>`/`<h1>` says "page not found" | **broken** (soft 404) | SPAs answer 200 for any path — `pretzel.rocks/library` did exactly this |
  | 200 with no `<title>` and no `<h1>` in the HTML | blocked (JS shell) | cannot be confirmed without a browser; set `linkcheck_js: true` once a human has looked |
  | redirect onto a different registrable domain | blocked (rebrand?) | e.g. `anthonyboyd.graphics` → `minimalmockups.com`, `freepik.com` → `magnific.com` |
  | any other redirect | ok, with the final URL in the report | so a silent move is still visible |
  | 404 on `HEAD` | re-checked with `GET` | some servers reject `HEAD` only |
  | **an expired domain that now serves something else entirely** | **blocked** — see the title fingerprint below | the replacement site answers 200 with its own healthy `<title>`, which is indistinguishable from the resource still being there. Found on 2026-10-18: `teenyicons.com` serves a gambling site while the icon project lives on at its GitHub home. The entry was never in our data, but the same takeover on one of ours would have looked exactly as green — which is why the check below exists |

  **The title fingerprint covers that last row.** Every run records the `<title>` it saw for each URL in `linkcheck-titles.json`, and a later run compares. When a title loses nearly every shared word — overlap below `TITLE_CHANGE_THRESHOLD`, 0.2 — the entry is reported as **blocked**, not broken: a rebrand looks exactly like a takeover from here, so this asks for eyes rather than failing a build. A flagged entry deliberately keeps its **old** fingerprint, so the next run flags it again instead of quietly re-baselining onto whatever took the domain over.

  Titles are compared as words; a script written without spaces (Chinese, Japanese, Korean) has no words to split on, so it is compared as overlapping **two-character grams** instead. That keeps `阿里巴巴普惠体` from scoring 0 against itself — which it did, and every Chinese entry was reported as changed on every run — while still separating `阿里巴巴普惠体` from `阿里巴巴图标库` (1/3 shared) and an unrelated title (0).

  The weekly job lists anything flagged in its step summary and opens (or comments on) an issue labelled `needs-review`. **After you have looked at one**, either fix the entry — a new URL, or remove it — or accept the new title:

  ```bash
  python3 scripts/linkcheck.py --slug fonts --accept-titles   # the same filters as the run that flagged it
  ```

  Two limits worth knowing. A title that is generic (`Home`) and later becomes a different generic title will be flagged once, wrongly — that is the cost of catching the real case. And nothing is recorded for an entry that came back `blocked` (bot wall, JS shell), so a hijacked domain behind Cloudflare stays invisible: this catches the takeover that still serves HTML, not the one hiding behind a challenge.

## Style

- Descriptions in English, imperative-free, no marketing fluff ("amazing", "best").
- Adding `description_zh` (and `notes_zh` when you add `notes`) is very welcome — native wording beats machine translation. The build warns when a translation is missing but never fails on it.
- One fact per entry; if a site has a separate free section, link **to the free section** when a stable URL for it exists — e.g. `https://www.motionelements.com/free/stock-footage`, `https://www.vecteezy.com/free-vector`. A green `linkcheck.py` is necessary but nowhere near sufficient: three kinds of page pass it and are still useless.

  | Trap | Real example from this repo | Does `linkcheck.py` catch it? |
  | --- | --- | --- |
  | Server-rendered soft 404 — HTTP 200, but the `<title>`/`<h1>` says "not found" | `pretzel.rocks/library`, `own3d.pro/en/free` | **yes** — reported as `broken` |
  | Client-side soft 404 — 200 with a normal marketing `<title>`, then the JS router renders the error page | `placeit.net/c/free` | no — open it in a browser |
  | A perfectly valid page whose listing is **empty** | `itch.io/game-assets/free/tag-twitch-overlay` (0 results, while `/tag-twitch` has 69) | no — count the results yourself |

  Also bot walls: some sites (Flaticon, Magnific/Freepik, ZapSplat, Motion Array, Nerd Or Die) return `403` to non-browser clients for *every* page including the homepage. `linkcheck.py` reports those as *blocked*, which does not fail CI but proves nothing either — read the licence with a real browser or skip the entry. And near-miss paths fail silently: Vecteezy's `/free-vectors` (plural) is dead while `/free-vector` (singular) is live.

  Because of the empty-listing trap, **prefer a section root over a filtered/tag URL**: tag listings empty out as sites change and nothing in CI will notice. If you cannot confirm a free-section URL, keep the homepage and say in `notes` how to reach the free assets. Never paper over it with `skip_linkcheck` — that field is for login walls only. Motion Array is the standing example: it has **no** combined free-browse URL any more (`/browse/free/` is its own 404, `/free/` 301s to the homepage), only bot-walled per-category pages such as `/after-effects-templates/free/`, so its entry stays on the homepage.
- Prefer the resource's own domain over aggregators, except for aggregator-type entries (search engines).

## Website

The interactive directory at https://skyzhao1223.github.io/free-for-creators/ is a dependency-free single-page app ([`site/index.html`](site/index.html)) that fetches the very same `data/*.json` at runtime — no second source of truth. Two scripts produce everything the deployed site needs:

```bash
python3 scripts/build_site.py      # site/data/*.json + site/all.html + site/sitemap.xml
python3 scripts/build_llms.py      # site/llms.txt + site/llms-full.txt
python3 -m http.server -d site 8000   # open http://localhost:8000
```

All seven outputs are **gitignored** and regenerated by the [Pages workflow](.github/workflows/pages.yml) on every deploy — so adding an entry never requires you to run them, and CI cannot fail on them:

- `site/data/` — per-category copies plus generated `manifest.json` and `all.json` (every category merged into one file, handy for programmatic use), and `experiences.json` (the creator field notes the interactive page renders).
- `site/all.html` — a fully static, no-JavaScript mirror of every entry, because `index.html` renders client-side and a crawler that does not run JavaScript would otherwise see an empty directory. It carries the `ItemList`/`Dataset` JSON-LD with live counts.
- `site/sitemap.xml` — both URLs, with `<lastmod>` taken from the last commit that touched `data/`.
- `site/llms.txt` — the [llmstxt.org](https://llmstxt.org) summary: what the directory is, the derived counts, the last link-check date, where the JSON lives, and how to cite an entry (name the license and attribution rule, link the resource — not us).
- `site/llms-full.txt` — every entry in one file as `license | attribution | monetized | sign-up | URL`, so a model can quote a column without fetching anything. `build_llms.py` imports `build_readme`, so the counts cannot drift from the READMEs.
- `site/changelog.html` — every entry added, corrected or removed, newest first, derived from the commits that touched `data/`. It reuses the PR contract's entry diff (`scripts/check_pr.py`), so "what changed" means the same thing to the changelog and to the gate.
- `site/feed.xml` — the same history as an Atom feed, capped at the last 50 changes, for anyone who would rather subscribe to a directory that grows a few entries a week than re-read it.

These are deliberately *not* committed: `all.html` and `sitemap.xml` embed that `lastmod`, and the commit which regenerates them is itself a commit touching `data/` — a checked-in copy could never agree with what CI computes, so every data change would fail its own sync check. The `llms*.txt` pair embeds today's counts for the same reason. Only `index.html`, `404.html` and `robots.txt` are hand-maintained, and `robots.txt` points crawlers at the llms pair.

Run `python3 scripts/build_site.py --check` any time to find out whether your local `site/` preview has gone stale. The script also fails if `CAT_COLORS` in `site/index.html` does not cover every slug in `CATEGORY_ORDER` — that map is the one site-side constant you must update by hand when adding a category.

### Responsive check

`python3 scripts/check_responsive.py` opens every page in headless Chrome at each breakpoint in the stylesheets — plus both neighbours of each, because an off-by-one at a media query is where this bug lives — and fails if the *document* can scroll sideways at any of them.

Nothing else can see that class of bug. It is invisible in a diff, absent from any desktop screenshot in a PR, and it only appears at a boundary width. Two shipped: `site/all.html`'s tables could not shrink below their ~520-630px min-content, so a 320px phone got a 649px document (329px of sideways scroll on every table); and `site/index.html`'s table kept `min-width: 900px` because the intended `@media (max-width: 760px)` override was written as `.tbl` and quietly lost the specificity fight with the base rule `table.tbl`, which put 98px of sideways scroll on a 768px iPad — in the view that page *defaults* to at that width.

It needs the built payload (`python3 scripts/build_site.py`) and any Chrome on your `PATH`; `--chrome /path/to/chrome` overrides the search, `--widths 320,760` narrows the run while you iterate, and `--verbose` prints every case. CI runs it as the `responsive` job in [`ci.yml`](.github/workflows/ci.yml).

## Creator field notes

The website's "Creator field notes" section is the one place the directory carries other people's words: short, first-hand write-ups about using a listed resource — what someone made, whether the licence held up in practice, what they wish they had known. It is fed by [the experience issue form](.github/ISSUE_TEMPLATE/share-experience.yml), not by resource PRs.

How a note gets published:

1. Someone opens the issue form — the "✍️ Share your experience" button on the site, or the "Share how a resource worked out" link on the new-issue page. The form asks which resource (its URL, copied verbatim), the project, the experience, and when it happened.
2. A maintainer reads the thread. A note is published as one person's experience, so it never overrides an entry's licence columns; if it contradicts one, fix the entry first.
3. The maintainer adds a record to [`data/experiences/notes.json`](data/experiences/notes.json) and runs:

   ```bash
   python3 scripts/experiences.py --check   # id, anchor, evidence, lengths, dates
   python3 scripts/build_readme.py          # regenerate both READMEs
   python3 scripts/build_site.py            # local preview (deploy-time output)
   ```

4. The note then appears in both READMEs, in `site/all.html` for crawlers, and on the site itself.

`data/experiences/notes.json` is deliberately a second store: `build_readme.load_categories()` reads every `data/*.json` as a category file, and `check_pr.py` reads the same directory as the entry diff — a subdirectory is invisible to both, which is what a differently-shaped store needs. A record looks like this:

```json
{
  "id": "google-fonts-video-subtitles",
  "entry_url": "https://fonts.google.com/",
  "author": "skyzhao1223",
  "lang": "zh",
  "date": "2026-03-11",
  "title": "用它的中文字体做了整套视频字幕",
  "body": "One paragraph, 80-800 characters: what you made, what the licence looked like in practice, what went wrong.",
  "tags": ["视频字幕", "商用"],
  "evidence": "https://github.com/skyzhao1223/free-for-creators/issues/1",
  "reviewed_by": "skyzhao1223",
  "reviewed_on": "2026-03-12"
}
```

Rules `scripts/experiences.py` enforces in CI:

- `entry_url` must be the **verbatim** URL of an entry in `data/*.json`. Rename or remove that entry and the note fails CI instead of quietly orphaning a card.
- `evidence` must be an issue, discussion or PR **in this repository** — a published note always has a thread a reader can check, and that is also what makes it revertible.
- `id` is a unique lower-kebab slug. `date` and `reviewed_on` must be real dates, never in the future, and review cannot precede the experience.
- `body` is one paragraph of 80-800 characters with no line breaks; `title` is 6-90 characters and may not contain a pipe character (it would break the README list). At most three tags of 2-16 characters.
- Notes are rendered in the language they were written in; the other language is not machine-translated.

Rejected in review even when CI would pass: press releases, affiliate or referral links, "commercially fine" claims the entry's licence columns do not support, and notes about a site that is not in this directory.

## Adding a category

1. Create `data/<slug>.json` (slug must match the filename and `^[a-z0-9]+(-[a-z0-9]+)*$`).
2. Add the slug to `CATEGORY_ORDER` in `scripts/build_readme.py`.
3. Add a colour for it in `CAT_COLORS` in `site/index.html` (CI enforces this).
4. Run `python3 scripts/build_readme.py` and commit the regenerated READMEs. (`scripts/build_site.py` needs no commit — its output is deploy-time only — but CI does check `CAT_COLORS`, so run it once locally to be sure.)

## Social preview & banner

The hero image (`assets/banner.png`, used in both READMEs) and the GitHub social preview (`assets/social-preview.png`, 1280×640) are rendered from [`assets/social-preview.html`](assets/social-preview.html).

**You normally do not render them yourself.** The counts inside that HTML are stamped from `data/` by `python3 scripts/build_readme.py`, and the [`Render banner`](.github/workflows/banner.yml) workflow re-renders all three images on any push that touches `data/`, `assets/social-preview.html` or the generator, then commits them back with `[skip ci]`. Add an entry, merge, and the images follow on their own.

Rendering locally and committing is now the *wrong* direction: the workflow compares bytes, so a local render reads as drift and gets committed over. The recipe below is a fallback for working without Actions.

<details>
<summary>Manual render (fallback only)</summary>

```bash
python3 scripts/build_readme.py   # stamps the counts into assets/social-preview.html
cd assets
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu \
  --hide-scrollbars --force-device-scale-factor=2 --window-size=1280,640 \
  --screenshot=social-preview@2x.png "file://$PWD/social-preview.html"
sips -z 640 1280 social-preview@2x.png --out social-preview.png
cp social-preview@2x.png banner.png
cwebp -q 90 -sharp_yuv banner.png -o banner.webp   # README hero: 646 KB PNG -> 158 KB, same 2560x1280
```

Note that `sips` is macOS-only; on Linux use Pillow (`im.resize((1280, 640), Image.LANCZOS)`), which is what the workflow does.

</details>

**The fonts are an implicit dependency, so they are asserted rather than pinned.** The HTML's font stack names only Apple faces, so on a Linux runner the Latin text falls through to the generic `sans-serif`, which fontconfig resolves to DejaVu Sans. Noto Sans CJK SC covers the four Han characters and Noto Color Emoji the seven emoji; the workflow installs both. Naming `DejaVu Sans` in the stack is *not* equivalent to inheriting it — Chrome resolves a named family differently from a generic one, and pinning it moved the render 8.75% of pixels away from the artwork that had been reviewed. So the stack stays generic and the workflow fails loudly if `fc-match sans-serif` ever resolves to anything else.

**Order matters if you do render manually: re-run `python3 scripts/build_site.py` *after* rendering.** `build_site.py` byte-copies `assets/social-preview.png` into `site/`, because the deployed `og:image` has to be served from Pages rather than from `raw.githubusercontent.com` (which GitHub proxies and re-encodes). Running it before the render therefore leaves `site/social-preview.png` holding the *previous* count. Deployments are unaffected — `pages.yml` builds after checkout — so this only makes the local preview disagree with what Pages serves. `python3 scripts/build_site.py --check` compares the two byte-for-byte and reports `stale: social-preview.png (missing or differs from assets/)`, so run it after re-rendering to confirm.

`social-preview@2x.png` is a local intermediate and is gitignored — `banner.png` *is* that 2× render, so committing both used to store the same 646 KB twice.

`banner.webp` is what both READMEs actually display (see the `<img src>` in `scripts/build_readme.py`). Keep both flags: `-sharp_yuv` matters more than the quality number here, because the hero is full of saturated colour (emoji, category dots) and WebP's 4:2:0 chroma subsampling is what eats those edges — not quantisation. Raising `-q` does not fix it (`-q 98` still peaks at a per-channel delta of ~87), while `-sharp_yuv` cuts it roughly in half for ~6% more bytes.

Measured against the PNG **at the 860×430 size the README actually renders** (per-channel delta, which is what an eye would see):

| cwebp flags | size | max delta | pixels >8 |
| --- | --- | --- | --- |
| `-q 92` | 156 KB | 33 | 0.29% |
| **`-q 90 -sharp_yuv`** | **148 KB** | **19** | **0.05%** |
| `-q 95 -sharp_yuv` | 203 KB | 18 | 0.04% |
| `-near_lossless 60` | 383 KB | 3 | 0.00% |

The table is a *relative* comparison between flag settings, which is its point; the absolute sizes were measured on the macOS/SF Pro render that was current at the time. The committed artwork is now the CI render, whose Latin text is DejaVu Sans, and its WebP is 158 KB rather than 148 KB. That is the glyphs carrying more ink, not the encoder differing: encoding the CI PNG with a local `cwebp` reproduces the runner's 158,468-byte output exactly. Sizes here are decimal kilobytes, as elsewhere in this file.

`banner.png` is kept as the WebP's source and as a one-line fallback: if a GitHub image proxy ever stops serving WebP, point `build_readme.py` back at it and regenerate. Do not downscale below 1720×860; the README renders the hero at `width="860"`, so that is the 2× retina floor.

Then re-upload `social-preview.png` under repo **Settings → General → Social preview** (GitHub accepts PNG/JPG/GIF only, max 1 MB — WebP is *not* accepted there, which is why the PNG stays).

**The artwork's geometry is checked, not just its pixels.** [`banner.yml`](.github/workflows/banner.yml) already rejects a blank or tofu render by colour count, ink coverage and saturation — none of which can see the failure mode that a growing directory creates: the artboard draws **one chip per category** in a flex row with a fixed `max-width`, so adding a category wraps the row onto another line. The pixels stay colourful and every colour check still passes; only the boxes move. [`scripts/check_banner.py`](scripts/check_banner.py) drives the same headless Chrome, reads the laid-out boxes back out of the DOM, and fails when the row overflows, leaves the artboard, collides with the table card, or exceeds `MAX_CHIP_ROWS` (3 today, with 11 categories). That constant is meant to be raised deliberately — it is the point at which somebody has looked at the picture after adding a category.
